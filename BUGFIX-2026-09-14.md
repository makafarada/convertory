# PDF to Word save repair

Scope: localhost:4755 web preview, not the installed Android application.

Confirmed failures:
- The server deleted a staged download after the first GET, so later Save attempts returned 404.
- In-app browser blob downloads did not trigger a download event or create a file in Downloads.
- The previously selected belge.pdf failed PDF signature validation. Its source contents were not available for diagnosis.

Changes:
- Retain staged downloads for their existing ten-minute lifetime.
- Explicit Save actions use a local POST endpoint and confirm the actual saved filename in Downloads/Convertory.
- Fetch and validate DOCX ZIP signature before reporting conversion success.
- Encode Unicode output names and use RFC 5987 download filenames.
- Disable duplicate conversion clicks, restore controls on failure, and bound client requests with timeouts.

Validation:
- Node syntax checks passed for app.js and preview-server.mjs.
- tests/pdf-download.integration.mjs passed with the user's document.pdf: 384675-byte output, repeated downloads identical, Unicode filename, explicit save, and invalid input rejected.
- All ZIP entries and XML parsed. Output contains 4838 editable text characters, seven tables, and verified Turkish words; no preview-export placeholder text.
- Actual in-app UI: Choose File -> Convert Now -> Save file -> My Files -> Save succeeded.
- Final UI-saved document (7).docx has valid ZIP/XML; its document XML and every embedded image match the validated output. Whole-file hashes across separate conversions differ because ZIP metadata varies.

Limits: this verifies PDF-to-Word conversion and saving for this source. Exact visual fidelity, Microsoft Word rendering, other conversion formats, and native Android were not validated in this change. Saved files remain on disk; in-memory history resets on page reload and staged Save links expire after ten minutes.
